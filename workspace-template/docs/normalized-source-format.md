# Normalized Source Format

Normalized source records are agent-readable Markdown files generated from manifest records. They live under `sources/normalized/` and provide the stable input layer for source notes, claim extraction, local search, and linting.

Raw files stay immutable under `raw/`. Normalized files may be regenerated by normalization tooling. Curated interpretation belongs in `wiki/sources/`, not in normalized records.

## Contract Status and Versioning

This document is a **versioned public contract**, not internal documentation. A record
that conforms to it is treated as first-class evidence regardless of which tool wrote
it, so an external normalizer can produce records for source kinds this package does
not extract itself — structured API payloads, instrument output, financial statements —
without forking the package or tracking its internals.

The contract version is declared per record in `normalized_format`:

| Version | Meaning |
|---------|---------|
| `1` | The contract described by this document. |
| absent | Legacy record written before the contract was versioned. Accepted only from this package's own normalizer (`normalizer.name: normalize_sources.py` or `manual`); re-normalization backfills the field. |

`normalize_sources.py` declares the versions it accepts in
`ACCEPTED_NORMALIZED_FORMATS` and stamps `NORMALIZED_FORMAT_VERSION` into every record
it writes. `evidence-wiki contract` reports both under
`normalized_source_format`, so a host can check compatibility before writing records.

`normalized_format` and `normalizer` answer different questions and move
independently. `normalizer` records *who produced* a record, and for records this
package produces it is also the regeneration trigger: a run re-normalizes any record
whose stored `normalizer.version` differs from the running normalizer's.
`normalized_format` records *which contract shape* a record claims, and is the only
field an external writer must track. A hand-written or externally produced record
carries its own `normalizer.name`/`version`, which the package never interprets as a
version of itself.

An externally written record must declare `normalized_format`. The legacy-absent rule
above exists to carry this package's own pre-contract records forward, not to let a
foreign record decline to state which contract it targets.

The rule exempts a legacy record from the version check only. Every other check still
applies, so a record written before a required field existed can still be reported by
`normalize_verify.py` — for example one predating `evidence_usable`. That is transient
and self-repairing: the first run after upgrading re-normalizes every record this
package produced, and the regenerated record carries the field. Lint does not report it
in the meantime, because lint holds only externally produced records to the contract.

## File Path

Use one normalized file per manifest source ID:

```text
sources/normalized/<safe-source-id>.md
```

`<safe-source-id>` is the manifest `id` made filesystem-safe:

- replace `:` with `--`;
- replace `/` and whitespace with `-`;
- keep lowercase letters, numbers, `.`, `_`, and `-`;
- collapse repeated `-`.

Examples:

| Source ID | Normalized Path |
|-----------|-----------------|
| `paper:2604.13018v1` | `sources/normalized/paper--2604.13018v1.md` |
| `link:github-aweai-team-aiscientist-a1b2c3d4e5` | `sources/normalized/link--github-aweai-team-aiscientist-a1b2c3d4e5.md` |
| `manual:lab-notes-agent-evals` | `sources/normalized/manual--lab-notes-agent-evals.md` |

## Frontmatter

Every normalized record must start with YAML frontmatter.

Required fields:

```yaml
---
type: normalized_source
normalized_format: 1
source_id: paper:2604.13018v1
source_kind: paper
status: content_extracted
evidence_usable: true
unusable_evidence_reasons: null
created: 2026-05-09
updated: 2026-05-09
normalized_at: 2026-05-09T12:00:00Z
raw_paths:
  - raw/other/arXiv-2604.13018v1
  - raw/pdf/2604.13018v1.pdf
manifest_path: sources/manifest.jsonl
normalizer:
  name: normalize_sources.py
  version: 3
parse_warnings: []
---
```

Required field meanings:

| Field | Meaning |
|-------|---------|
| `type` | Always `normalized_source`. |
| `normalized_format` | Contract version this record claims. See "Contract Status and Versioning". Required for records written outside this package; absent means a legacy record from this package's own normalizer. |
| `source_id` | Exact manifest `id`, or a stable manual ID for manual records. |
| `source_kind` | Manifest `kind`, such as `paper`, `pdf`, `repo_link`, `web_link`, `codebase_architecture`, or `manual_note`. |
| `status` | Normalization lifecycle status. |
| `evidence_usable` | `true` when the normalized record can be considered by coverage policies, `false` when delivery metadata or deterministic HTML checks mark it as unusable evidence. |
| `unusable_evidence_reasons` | Stable reason codes when `evidence_usable` is `false`; otherwise `null` or omitted in older records. |
| `created` | Date the normalized record was first created, `YYYY-MM-DD`. |
| `updated` | Date the normalized record was last updated, `YYYY-MM-DD`. |
| `normalized_at` | Exact UTC timestamp when `normalize_sources.py` wrote or updated the record, `YYYY-MM-DDTHH:MM:SSZ`. Legacy records created before this field existed may omit it. |
| `raw_paths` | Workspace-relative raw paths used as evidence. Empty only for manual records. |
| `manifest_path` | Workspace-relative manifest path, usually `sources/manifest.jsonl`. |
| `normalizer` | Tool name and version that produced the record. For externally produced records this names the external tool; the package stores it and never reads it as a version of itself. |
| `parse_warnings` | List of non-fatal extraction issues. Use `[]` when clean. |

Allowed `status` values:

| Status | Meaning |
|--------|---------|
| `stubbed` | Source is represented but content was not fetched or extracted. |
| `content_extracted` | Main source content was extracted into Markdown. |
| `partial` | Some content was extracted, but important parts are missing or unreliable. |
| `failed` | Extraction failed; the record exists to preserve evidence and warnings. |

Optional field meanings:

| Field | Meaning |
|-------|---------|
| `title`, `authors`, `venue`, `date`, `doi`, `arxiv_id`, `openalex_id`, `url` | Citation metadata when available. Provider-acquired PDFs prefer provider `title`/`authors`/identifiers over PDF heuristics so live citation verification compares authoritative identity metadata. |
| `title_source` | Where the normalized title came from. `provider` means arXiv/OpenAlex provenance supplied the identity title; `pdf_inference` means the title was inferred from PDF text. |
| `extracted_title` | PDF-inferred title retained for diagnostics when `title_source: provider` replaces it, or for manual PDF deliveries that still rely on PDF title inference. |
| `title_confidence` | How far to trust an inferred title: `high`, `low`, or `none` (the record fell back to its source id). Written for `extraction_method: pdf_text` records, where the title comes from heuristics over extracted text rather than from provider metadata. A `low` or `none` value also raises LOW `pdf_title_uncertain` in lint. |
| `raw_pdf`, `latex_root`, `entrypoint` | Source-specific raw locations from the manifest. |
| `repo_full_name` | GitHub owner/repository for repository links. |
| `codebase_repo`, `codebase_revision`, `codebase_tool`, `codebase_artifact_paths` | Optional metadata for normalized codebase architecture records. `codebase_artifact_paths` lists the deposited artifact files the intake pass collected, workspace-relative, excluding the manifest itself. |
| `codebase_intake_status` | Verdict of the bounded artifact intake: `validated` (an `artifact-manifest.json` was present and every deposited file matched its declared checksum and size), `legacy_unbound` (artifacts exist but no manifest does, so they are unverified evidence), `invalid` (the bundle broke a bound or a manifest check — no artifact is read and the record becomes a `codebase_stub`), or `missing` (no artifact directory). Each failure is also restated in `parse_warnings`. |
| `codebase_execution_scope` | Always `external_worker_only`. A standing statement, not a computed value: this package reads deposited artifacts and never runs the codebase tool, clones a repository, or fetches network content. A separately authorized external worker produces the artifact out of band. |
| `codebase_artifact_manifest`, `codebase_artifact_checksums`, `codebase_artifact_provenance` | Produced together by the intake pass. `codebase_artifact_manifest` is the workspace-relative path of the deposited `artifact-manifest.json`; `codebase_artifact_checksums` is one `{path, sha256, size_bytes}` entry per accepted file, verified against the manifest when `codebase_intake_status: validated`; `codebase_artifact_provenance` carries the manifest's `producer` name/version, `generated_at`, and the `invocation` block (`argv`, `executed_by: external_worker`, and `plugins_enabled`/`hooks_enabled`/`network_access`, all required to be `false`). Its `trust: self_asserted_external_worker` is literal — the worker asserts how it ran, and this package records the assertion rather than confirming it. |
| `provider` | Inferred provider for link stubs, such as `github` or a URL host. |
| `fetch_status` | Fetch or artifact state for link and codebase stubs. Use `not_fetched` when no network content has been fetched and `artifact_recorded` when a local codebase artifact was normalized. |
| `extraction_method` | Method used, such as `latex`, `pdf_text`, `html_text`, `table_text`, `link_stub`, `manual`, `web_stub`, `codebase_context`, or `codebase_stub`. |
| `pdf_extractor` | PDF records only: the selected backend `name` (`pypdf` or `poppler`) and resolved backend `version`. Changing the configured backend makes an existing PDF record stale and regenerates it. |
| `content_hash` | Hash of normalized extracted content for reproducibility. |
| `raw_fingerprint` | Content hash of the raw inputs (paper bundle, PDF, HTML page, or CSV/TSV file) copied from the manifest. Re-running normalization compares it to the manifest to re-generate only records whose raw source changed. Absent for links and codebase records. |
| `references_source_ids` | Matched citation-graph neighbors from local BibTeX bibliographies. v1 matches only arXiv IDs and DOI strings against existing manifest records; no title, author, or fuzzy matching is performed. |
| `academic` | Provider-backed publication metadata copied from provenance when available: provider, source type, venue, publication year, OA status, peer-review/publication status, and provider ids. |
| `standards` | Standards-registry metadata copied from `provenance.standards` when available. Typical fields include registry provider, standards body, designation, title, edition or year, status, registry URL, product category, legal act, OJEU reference, dataset license, and replacement-chain fields. |
| `provenance` | Delivery provenance copied from the manifest record when a provenance sidecar was delivered with the raw source (see [source-delivery.md](source-delivery.md)). Carries `origin_url`, `license`, academic metadata, standards metadata, currentness metadata, OpenAlex enrichment diagnostics (`provider_license_slug`, `license_source`, `openalex_title_lag`, `openalex_identity_conflict`, reported OpenAlex title/authors/year, `openalex_identity_evidence`, and `doi_resolution`), `evidence_usability_override`, and optional source-delivery failure fields into exported citations. When a complete audited override clears a deterministic JavaScript-shell false positive, normalized frontmatter also records `evidence_usability_override_applied: true` inside this block. Valid failure codes are `tls_verification_failed`, `http_error`, `javascript_required`, `official_error_page`, `not_found`, `content_too_sparse`, `license_or_terms_unknown`, `robots_or_terms_blocked`, and `manual_review_required`. |
| `rendered_coverage` | How much of a structured payload the record's body renders verbatim, and which facets lost content. Required for `extraction_method: adapter`, optional elsewhere but checked whenever declared. See "Rendered coverage" for the shape and the compliance floor. |
| `needs_ocr` | `true` when PDF extraction ran successfully but produced near-empty text (likely a scanned or image-only PDF). See "Scanned PDFs and OCR". |
| `language` | BCP-47 language tag when known. |
| `confidence` | `high`, `medium`, or `low` extraction confidence. |
| `abstract_confidence` | PDF abstract extraction confidence. `low` means a fallback heuristic recovered text after heading reordering and the record carries a parse warning. |

`normalize_sources.py` keeps extraction `status` separate from evidence
usability. A successfully parsed official error page can still have
`status: content_extracted`, but it carries `evidence_usable: false` so
coverage policies reject it. The normalizer copies inventory usability reasons
from the manifest and adds conservative HTML reasons for obvious 404/not-found
pages, official unavailable/error pages, and sparse JavaScript shells.

## PDF Text Extraction Backends

PDF-only records use `extraction_method: pdf_text` when no usable LaTeX
entrypoint exists. `sources.pdf_extractor` selects the backend for a workspace;
the template default is `pypdf`. One command can override that reviewed setting
with `--pdf-extractor pypdf|poppler`. The selected backend and version are
recorded in `pdf_extractor` frontmatter and in the JSON action report. Changing
the selection makes existing PDF records stale so they are regenerated instead
of silently retaining text produced by another backend.

### Portable pypdf backend

pypdf 6.14 or newer within major version 6 is a required EvidenceWiki Python
dependency and is installed by pip with the package. Extraction runs in a
separate isolated invocation of the exact Python interpreter. It performs two
bounded passes per page:

- the plain `page.extract_text()` pass supplies reading-order source text;
- `page.extract_text(extraction_mode="layout",
  layout_mode_space_vertically=False)` supplies layout text used only for
  media and table captions.

The helper has a 120-second timeout and refuses PDFs larger than 100 MiB, more
than 2,000 pages, or more than 20,000,000 extracted characters per pass. Its
structured result is validated before normalization. A missing pypdf install is
a fatal setup error and, under `--format json`, is emitted on stderr through the
shared error envelope. A corrupt, timed-out, or otherwise failed individual PDF
is retained as a failed action in the normalization report, and the command
exits non-zero; no stub is presented as normalized evidence.

### Explicit Poppler compatibility backend

`poppler` is opt-in and uses the local Poppler executable for equivalent
reading-order and layout passes:

```text
pdftotext -enc UTF-8 <pdf> -
pdftotext -enc UTF-8 -layout <pdf> -
```

pip cannot install this system executable. Install it separately with
`poppler-utils` on Debian/Ubuntu, `brew install poppler` on macOS, or
`conda install conda-forge::poppler` on Windows. Selecting `poppler` when
`pdftotext` is not on `PATH` is a fatal setup error; missing Poppler has no
effect when the default pypdf backend is selected.

Both backends feed the same deterministic cleanup and metadata heuristics. The
normalizer strips arXiv sidebar watermark lines, joins simple mid-word
hyphenation breaks, handles ICML-style abstract boxes that appear after an
Introduction heading, and lowers title confidence when it collapses
letter-spaced small-caps title fragments. When the ICML-style abstract fallback
fires, normalized frontmatter records `abstract_confidence: low` and a parse
warning names the recovery heuristic.

PDF extraction changes normalized evidence text. After changing PDF extraction behavior or regenerating PDF-fallback normalized records, rerun `verify_quotes.py --slug <slug> --write` for every grounded question that cites those records before the next readiness evaluation.

## Scanned PDFs and OCR

When the selected PDF extractor runs successfully but extracts fewer than 100
characters per page (`PDF_MIN_CHARS_PER_PAGE` in `normalize_sources.py`), the
PDF is likely scanned or image-only. The record is still written, clearly
degraded:

- frontmatter gains `needs_ocr: true` and a parse warning naming the character and page counts;
- record `status` is `partial` (not `failed`), so orchestrators can distinguish "needs OCR" from broken extraction;
- `confidence` is `low`.

`workspace_status.py` reports the count of such records as `sources.needs_ocr`, and lint raises a LOW `pdf_needs_ocr` notice per record, so an orchestrator can route an OCR task.

OCR itself is out of scope: no OCR dependency is bundled. The supported route
is external — a user or agent runs OCR out of band and delivers the extracted
text alongside the PDF (for example as a Markdown file under the same raw root,
or as a `manual:` normalized record). Environment or execution failures
(missing selected backend, timeout, corrupt PDF, or non-zero extractor exit)
never set `needs_ocr`; those remain failed actions.

## HTML Records

Sources classified as `html` (`.html`, `.htm`, `.xhtml`) are normalized with `extraction_method: html_text` using the Python standard-library parser:

- `<title>` becomes the record title (fallback: first heading, then file name, with a parse warning naming the fallback). The fallback is recorded in `parse_warnings` only: `title_confidence` is written for PDF records and stays `null` here, so a reader checking how far to trust an HTML title reads the warnings;
- `<h1>`–`<h3>` headings become the outline (capped at 80 entries);
- visible body text becomes the extracted text — content inside `script`, `style`, `nav`, `noscript`, `template`, `svg`, and `iframe` is dropped;
- absolute `http(s)` URLs from `<a href>` become the links section (capped at 100);
- `<meta name="description">` becomes the abstract when present.

Boundaries: extraction is deterministic and local-only. There is no JavaScript rendering and no remote asset fetching; a page that requires JS to render its content yields whatever static text is present. Files larger than 2 MB (`HTML_MAX_BYTES`) are truncated with a parse warning. Malformed markup degrades to body-text-with-warnings, never a crash. Single-file pages and arXiv HTML-format papers are both supported.

## Tabular Records (CSV/TSV)

Manifest `table` records with `.csv`/`.tsv` extensions are normalized with `extraction_method: table_text` using the standard-library `csv` module:

- the first row provides column names, listed in the extracted text so they are findable via `query_index.py`;
- the delimiter is sniffed (`,` `\t` `;` `|`), falling back by extension;
- the data row count is reported, and the first 20 rows (`TABLE_SAMPLE_ROWS`) are rendered as a Markdown sample table with cells capped at 80 characters;
- ragged rows (column count differing from the header) produce a parse warning naming the first offending line.

Files larger than 5 MB (`TABLE_MAX_BYTES`) are scanned only up to the cap, with a parse warning and the row count reported as a lower bound. Excel, Parquet, and Feather files remain classified-only: they get manifest records but no normalized record, because reading them would require new dependencies.

`.json` and `.jsonl` are not tabular records. They classify as `structured_data`, a kind this package does not extract, so they are classified-only until a workspace configures a normalization adapter for the kind or an external normalizer writes the record directly. See "Writing Records From an External Normalizer" and [research-yml.md](research-yml.md).

## Codebase Architecture Records

Codebase analysis is optional. Use `source_kind: codebase_architecture` when a repository, source archive, or implementation snapshot is research evidence.

Recommended rules:

- use read-only analysis commands when possible;
- store generated architecture output under `sources/`, not directly under the maintained `wiki/`;
- cite codebase analysis through source notes and `source_ids`;
- include `codebase_repo`, `codebase_revision`, and `codebase_tool` when known;
- preserve tool warnings and unsupported-language gaps in `parse_warnings`;
- do not install hooks or background sync while normalizing codebase evidence.

For `agent-wiki-cli` / `python-wiki-llm`, prefer `llm-wiki extract` and `llm-wiki context` output for normalized records. Use generated architecture wiki output only as a source artifact, for example under `sources/code_wikis/<source_id>/`.

`normalize_sources.py` reads local adapter artifacts only. It looks for preferred files such as `context.json`, `extract.json`, `summary.json`, `context.md`, `extract-summary.md`, or `summary.md` in the manifest record's `metadata.codebase_output_dir`. If no artifact exists, the normalizer writes a `codebase_stub` with a warning and the configured command as a manual next action. It never runs `llm-wiki`, clones repositories, fetches network content, or syncs a generated architecture wiki.

## Citation Graph References

For LaTeX paper records, normalization reads local `.bib` files named by
`\bibliography{...}` or `\addbibresource{...}` commands in the expanded source
bundle. Bibliography paths must stay inside the LaTeX bundle; unsafe or missing
files are ignored.

When a BibTeX entry contains a DOI (`doi`) or arXiv identifier (`eprint` with an
arXiv `archivePrefix` / `eprinttype`, or arXiv-like identifier fields), the
normalizer matches that identifier against the current source manifest. Only
existing manifest records are emitted in `references_source_ids`, self-citations
are skipped, and duplicate matches are collapsed in bibliography order. The
normalizer does not scan arbitrary extracted text for references and does not
perform title or author matching.

## Normalization CLI

Run normalization from the research workspace root:

```bash
python3 scripts/normalize_sources.py
```

Default behavior normalizes only pending eligible manifest records, meaning records whose normalized Markdown file does not already exist.

Common controls:

| Command | Behavior |
|---------|----------|
| `python3 scripts/normalize_sources.py` | Normalize pending eligible sources: those with no output yet, plus those whose raw inputs changed since they were last normalized (stale). |
| `python3 scripts/normalize_sources.py --source-id paper:2604.13018v1` | Normalize one source ID. |
| `python3 scripts/normalize_sources.py --source-id ID1 --source-id ID2` | Normalize a selected subset. |
| `python3 scripts/normalize_sources.py --all` | Consider all eligible sources. Missing and changed (stale) outputs are (re)generated; unchanged outputs are skipped unless `--force`. |
| `python3 scripts/normalize_sources.py --all --force` | Regenerate every eligible source, even unchanged ones. |
| `python3 scripts/normalize_sources.py --all --dry-run` | Print planned actions without extraction or writes. |
| `python3 scripts/normalize_sources.py --all --format json` | Print one machine-readable normalization report object to stdout. |
| `python3 scripts/normalize_sources.py --pdf-extractor poppler` | Explicitly use the optional Poppler compatibility backend for this run. |
| `python3 scripts/normalize_sources.py --append-log` | Append a compact run summary to `log.md`. |

Unchanged existing records are not overwritten unless `--force` is supplied. A
record is re-normalized automatically when its raw inputs change: inventory
records a `raw_fingerprint` (a content hash of the paper bundle, PDF, HTML
page, or CSV/TSV file) in the manifest, normalization stores the same value in
the record's frontmatter, and a later run regenerates any record whose stored
fingerprint no longer matches the manifest. Links and codebase records carry no
fingerprint and keep skip-if-exists behavior. Use `--force` with `--source-id`
for a precise refresh or with `--all` to regenerate everything. `--append-log`
is skipped during `--dry-run`.

The first run after upgrading the tooling re-normalizes existing paper and PDF
records once to backfill `raw_fingerprint`; later runs only touch changed
records.

Each run prints a stderr summary with selected, planned, created, updated,
skipped, stale, dry-run, method, partial, and failed counts.

Use `--format json` when an orchestrator needs machine-readable results. JSON
mode prints one object with `schema_version: "1.0"` and `document_type:
"source_normalization_report"`. The report includes the manifest path,
normalized-source directory, run flags, selected/planned/result counters,
method counts, top-level warnings, and one action record per selected source
that was skipped, planned, created, updated, partially extracted, or failed.
Action warnings include unusable-evidence reasons when normalization detects an
obvious official error page or sparse JavaScript shell.

`summary.methods` counts one key per extractor — `latex`, `pdf`, `links`, `html`,
`tables`, `codebase`, and `adapter` — and an action produced by an external normalizer
carries an `adapter` object naming the tool and version that produced it, so a report
reader can attribute a record without opening it. The same counters appear on the
stderr summary line and in the `log.md` entry written by `--append-log`.

`schema_version` is bumped only for breaking shape changes; new counters and action
fields are forward-compatible additions, so pin the major version and ignore unknown
keys rather than matching the document exactly.

Like every JSON surface in the workspace, this report is exactly one document on
stdout with diagnostics on stderr — see "Machine Output On stdout" in
[orchestrator-handoff.md](orchestrator-handoff.md).
Fatal setup and tooling errors under JSON mode, including a missing manifest,
missing required pypdf package, or missing `pdftotext` after explicitly
selecting Poppler, are written to stderr as the shared error envelope.
Per-source extraction failures remain structured failed report actions so an
orchestrator can route them to repair or manual review without scraping text;
the normalization command exits non-zero when any action failed.

## Writing Records From an External Normalizer

A workspace's evidence is not limited to the source kinds this package extracts. When
the evidence is a structured API payload, instrument output, or anything else
`normalize_sources.py` does not read, an external tool may write the normalized record
itself, and a record that conforms to this contract is evidence on exactly the same
terms as one this package produced.

That equality is earned per record, not granted by origin. Nothing is trusted because
of who wrote it: lint accepts a record from a foreign normalizer as it accepts a native
one **only when the record conforms**, and reports
`normalized_record_contract_violation` when it does not. `normalize_verify.py` is how
you check conformance before the workspace has to.

### What your record must carry

- `normalized_format: 1` — the contract version you are targeting. This is the only
  version field you track; see "Contract Status and Versioning".
- `normalizer.name` and `normalizer.version` naming **your** tool. Do not claim
  `normalize_sources.py`: that name marks a record as this package's own output, which
  changes how it is treated. The package stores your values and never reads them as a
  version of itself.
- Every required frontmatter field, with the documented types — including an explicit
  `evidence_usable`. It is required rather than defaulted, because a record that
  omitted it and read as usable would fail open past coverage policies.
- All eight required sections, in order. Extra headings inside a section are ordinary
  content; the required eight simply have to appear in sequence.
- Agreement with the manifest: the record lives at the path its `source_id` resolves
  to, lists every raw path the manifest records for that source, and — if it declares
  `raw_fingerprint` — matches the manifest's.

### Which sources you may write records for

Write records for sources nothing else normalizes. Those records are yours:
normalization never considers them, so they are never rewritten.

A record you write for a source that *is* normalized — by this package or by a
configured adapter — **will be overwritten** by the next `normalize_sources.py` run,
with no `--force` required. Two cases:

- Kinds this package extracts itself: `paper`, `pdf`, `repo_link`, `web_link`, `html`,
  and CSV/TSV `table`. A record whose `normalizer.version` is not the running
  normalizer's counts as stale, so the run regenerates it.
- Kinds mapped in `normalization.adapters`. Mapping a kind hands it to that adapter; a
  record naming any other producer is stale (see "When an adapter re-runs").

This is not a safeguard you can opt out of per record. Keep hand-written records to
kinds nothing normalizes, and use `wiki/sources/` for curated interpretation of
evidence that is normalized.

### Workflow

Deliver the raw evidence first, so the manifest record your normalized record must
agree with exists:

```bash
# 1. Deliver raw bytes + provenance sidecar (see source-delivery.md), then inventory:
python3 scripts/source_inventory.py --report

# 2. Write your normalized record at the path the source id resolves to.

# 3. Check it against this contract before relying on it:
python3 scripts/normalize_verify.py --source-id <source-id> --format json

# 4. Confirm the workspace agrees:
python3 scripts/lint.py --format json
```

A conforming record then behaves like any other evidence: `verify_quotes.py` verifies
quotes against its body, `question_resolve.py reopen` accepts it as delivered evidence
for a blocked question, and lint reports no contract finding for it.

## Normalizer Adapters

An external normalizer can also be run *by* the workspace rather than beside it. When
`research.yml` maps a source kind to an adapter (see
[research-yml.md](research-yml.md)), `normalize_sources.py` treats records of that kind
as ordinary work: they are selected, normalized, and re-normalized on staleness like
any other record.

The division of labour is deliberate. The adapter returns **content**; the package
writes the **record**. Frontmatter, section order, `raw_fingerprint`, `content_hash`,
and `created` are derived here from the manifest, so a buggy adapter cannot make a
record claim more than it earned. The record does name the adapter as its producer:
`normalizer` carries the adapter's configured identity, and `extraction_method` is
`adapter`.

### Request

The adapter is executed with `shell=False` from the argv list in `research.yml`, with
the workspace root as its working directory and a bounded timeout. One JSON document
arrives on stdin:

```json
{
  "schema_version": "1.0",
  "document_type": "normalizer_adapter_request",
  "normalized_format": 1,
  "project_root": "/abs/path/to/workspace",
  "manifest_record": { "id": "raw:...", "kind": "structured_data", "raw_paths": ["raw/data/x.json"] },
  "raw_paths": ["raw/data/x.json"]
}
```

### Response

Exactly one JSON document on stdout, and nothing else — diagnostics belong on stderr,
where they are captured into the record's parse warnings:

```json
{
  "schema_version": "1.0",
  "document_type": "normalizer_adapter_result",
  "adapter": {"name": "autoseller-normalize", "version": "1.4.0"},
  "status": "content_extracted",
  "title": "Keepa snapshot B0ABC",
  "abstract": "Supplier price snapshot.",
  "outline": [[3, "supplier_quote"], [3, "price_history"]],
  "body_markdown": "### supplier_quote\n\n- price: 23.99 EUR\n",
  "rendered_coverage": {
    "total_values": 1200,
    "rendered_values": 480,
    "ratio": 0.40,
    "sections": [
      {"heading": "supplier_quote", "total": 60, "rendered": 60},
      {"heading": "price_history", "total": 1140, "rendered": 420,
       "note": "capped to 90-day window; series collapsed to count beyond"}
    ]
  },
  "warnings": ["price series capped to 90 days"]
}
```

| Field | Rule |
|-------|------|
| `schema_version`, `document_type` | Exactly as shown. |
| `adapter` | Must equal the `name`/`version` `research.yml` authorized. A mismatch fails the action: the record's stated producer has to be the tool the workspace approved. |
| `status` | `content_extracted` or `partial`. The adapter's verdict is kept as the record's status, because a capped rendering looks complete from the outside. `failed` (with optional `detail`) reports that the adapter could not produce content. |
| `body_markdown` | Required, non-empty. Becomes the `Extracted Text` section. Facet headings must be `###` or deeper — a `##` heading would collide with the record's own eight sections. |
| `title`, `abstract` | Optional strings. |
| `outline` | Optional `[[level, text], …]`, rendered as the `Outline` section. |
| `rendered_coverage` | **Required.** What the rendering kept — see "Rendered coverage". Checked against the returned body before anything is written, so an incoherent claim fails the action. |
| `warnings` | Optional list of strings, kept in `parse_warnings` and restated in the record body. |

### Rendered coverage

A normalized body for structured evidence is a *rendering*, and a rendering has caps: a
90-day price series becomes a few readings and a count, a long array collapses. Grounding
is verified by containment against that body, so whatever the renderer dropped is
citable but **not quotable** — and without a record of it, that loss is invisible. A
record that rendered a tenth of its payload looks exactly like one that rendered all of
it.

`rendered_coverage` is the renderer's own statement of what it kept:

```yaml
rendered_coverage:
  total_values: 1200        # scalar leaves in the raw payload the renderer considered
  rendered_values: 480      # of those, present verbatim in the body
  ratio: 0.40
  sections:
    - heading: supplier_quote
      total: 60
      rendered: 60
    - heading: price_history
      total: 1140
      rendered: 420
      note: "capped to 90-day window; series collapsed to count beyond"
```

**Required** for records this package renders through an adapter
(`extraction_method: adapter`) — the protocol can demand it, and an adapter that renders
everything simply reports equal counts with `ratio: 1.0`. **Optional** for records
written by any other tool, which the package does not control; a block that *is* declared
is checked either way.

What a compliant renderer must do:

- Give every facet that coverage tooling can point a `location_hint` at its own heading
  in the body, so a claim can anchor there. Depth is free — use `###` or deeper, since
  `##` is reserved for the record's own sections.
- Record each cap as a section `note` saying what was dropped and why. A section that
  rendered nothing needs no heading in the body: there is nothing to point at, and the
  entry exists precisely to account for the loss.
- Leave the raw snapshot complete and immutable under `raw/`. Coverage describes the
  rendering, never the evidence: what the body omits is still in the raw file.

What the package checks (`normalize_verify.py`, and lint for foreign records): the block
is a mapping with non-negative `total_values`/`rendered_values` where rendered never
exceeds total; `ratio` matches those counts (`1.0` when nothing was considered, since a
renderer that dropped nothing lost nothing); section counts never exceed the record's
totals; and a section claiming rendered values names a heading the body actually has.
The counts themselves are not recomputed — this package cannot know a foreign renderer's
capping rules, which is why the renderer states them. Whether every coverage facet has a
section is prose above, not an automated check, because that needs the coverage manifest.

Rendered coverage keeps the text path honest; it does not make capped content quotable.
Anchoring a claim to a specific field, rather than to a line of rendered text, is what
CR-7's structured grounding anchors are for.

### When an adapter re-runs

Adapter records are versioned by their adapter, not by this package, so they are not
compared against the package's own `NORMALIZER_VERSION`. A normalization run re-executes
an adapter for a record only when:

- the adapter's configured `name` or `version` differs from what the record records as
  its producer — bump `version` in `research.yml` to force a rebuild after changing an
  adapter's behaviour; or
- the source's `raw_fingerprint` changed, meaning the delivered payload is not the one
  the record was built from.

Otherwise the record is left alone and reported as `skipped_existing`. `--force`
rebuilds regardless, as for any other kind.

This is also the boundary for hand-written records. A kind with **no** adapter mapped is
not eligible for normalization at all, so a record you write for it is never
regenerated — that is the safe place to write records yourself. Mapping a kind to an
adapter hands that kind to the adapter: a hand-written record for a mapped kind names a
producer the workspace did not authorize, so the next run replaces it.

### Failure is closed

An adapter run that cannot produce a fully understood result writes no record at all:
the run reports a failed action naming the reason and exits non-zero. That covers a
non-zero exit, a timeout, output that is not exactly one JSON document, an identity
mismatch, a `failed` status, a missing body, a `##` heading in the body, a missing or
incoherent `rendered_coverage`, and output beyond the size cap. A record that exists is
treated as evidence by grounding, by the
reopen gate, and by lint, so a partial or stub record would be worse than none. The
package also re-checks its own rendering against this contract after writing, and
removes the file if it does not conform.

## Verifying Records Against This Contract

`normalize_verify.py` checks records against this document and reports each breach with
a stable code, so a tool that writes records can prove they conform instead of matching
the format by inspection. It is offline, read-only, and checks a record written by an
external normalizer exactly as it checks one this package wrote.

```bash
python3 scripts/normalize_verify.py --format json
evidence-wiki normalize verify --target PATH --source-id data:keepa-b0abc123
```

| Command | Behavior |
|---------|----------|
| `normalize_verify.py` | Verify every record under the normalized directory. |
| `normalize_verify.py --all` | The same selection, stated explicitly. |
| `normalize_verify.py --source-id ID` | Verify one record. Repeatable. A source id that is neither in the manifest nor on disk is refused with `SOURCE_UNKNOWN`. |
| `normalize_verify.py --format text` | Human-readable summary instead of the JSON report. |
| `normalize_verify.py --output PATH` | Write the report to a file instead of stdout. |

The JSON report carries `document_type: "normalize_verify_report"`, the contract
versions it checked against, and one entry per record with its `origin`
(`native` or `external`), declared `normalized_format`, verdict, and violations. Each
violation names the offending `field`, what was `expected`, what was `actual`, and a
`remediation`. The command exits `0` when every selected record conforms, `1` when any
record is invalid, and `2` for a workspace it cannot read (missing `research.yml` or
manifest), which is reported as the shared error envelope on stderr.

A contract breach is report content, not a fatal error, so one malformed record never
hides the rest. Verifying a workspace with no normalized records succeeds and records a
warning; a caller that also requires evidence to exist reads `counts.records`.

Every record entry also carries `rendered_coverage`, so a host can see how much of a
source's structured content the body actually renders without opening the record:

```json
"rendered_coverage": {
  "ratio": 0.40,
  "total_values": 1200,
  "rendered_values": 480,
  "capped_sections": ["price_history"]
}
```

`capped_sections` names the facets that lost content — the parts a claim can cite but
never quote. The field is `null` for a record that declares no block, which is every
record that is not a rendering of structured evidence; that is different from a record
that rendered nothing. Coverage is reported for invalid records too, since an operator
triaging one still needs to know how much of it is quotable. The `--format text` report
states the same figures under each record.

Lint can report thin renderings as well, but only when asked: set
`lint.min_rendered_coverage_ratio` in `research.yml` and any record declaring a lower
ratio emits LOW `normalized_low_rendered_coverage`. It is off by default and LOW when it
fires, because capping a long series is a legitimate choice rather than a defect. Unlike
the contract check, it applies to native and foreign records alike.

Violation codes:

| Code | Meaning |
|------|---------|
| `NORMALIZED_CONTRACT_FRONTMATTER_MISSING` | The record is unreadable or has no usable YAML frontmatter block. |
| `NORMALIZED_CONTRACT_FRONTMATTER_INVALID` | A required frontmatter field is absent or has the wrong type or value. |
| `NORMALIZED_CONTRACT_FORMAT_VERSION_UNSUPPORTED` | `normalized_format` is absent from an externally written record, or declares a version this package does not accept. |
| `NORMALIZED_CONTRACT_SECTIONS_INVALID` | A required section is missing, or the required sections are out of order. |
| `NORMALIZED_CONTRACT_MANIFEST_MISMATCH` | The record disagrees with the manifest about its path, source id, raw paths, or raw fingerprint. |
| `NORMALIZED_CONTRACT_WARNINGS_INCONSISTENT` | A `parse_warnings` entry is not restated in the `Parse Warnings` section. |
| `NORMALIZED_CONTRACT_RENDERED_COVERAGE_INVALID` | `rendered_coverage` is absent from an adapter-rendered record, or its counts, ratio, or section headings do not describe the body. |

`evidence-wiki contract` reports the same code list under
`normalized_source_format.violation_codes`, so a host can handle them without scraping
text.

## Required Sections

Use these sections in this order. If a section has no content, write `None extracted.` or `None recorded.` rather than deleting the section.

```markdown
# <title or source_id>

## Citation Metadata

## Abstract

## Outline

## Extracted Text

## Figures and Tables

## Links

## Raw Source Paths

## Parse Warnings
```

Section expectations:

| Section | Content |
|---------|---------|
| `Citation Metadata` | Human-readable citation fields copied from frontmatter or extracted text. |
| `Abstract` | Source abstract, summary, or `None extracted.` |
| `Outline` | Section hierarchy or source structure. |
| `Extracted Text` | Main normalized source text. Preserve headings when possible. |
| `Figures and Tables` | Figure/table references, captions, labels, and extraction notes. |
| `Links` | URLs, repository links, arXiv links, project pages, or related raw links. |
| `Raw Source Paths` | Evidence paths from `raw_paths` plus any manifest source-specific paths. |
| `Parse Warnings` | Same warnings as frontmatter, with enough context for review. |

## Citation From Wiki Source Notes

Wiki source notes cite normalized records through `source_ids`:

```yaml
---
type: source
created: 2026-05-09
updated: 2026-05-09
source_ids:
  - paper:2604.13018v1
---
```

When a source note references `paper:2604.13018v1`, tooling should resolve the normalized record at:

```text
sources/normalized/paper--2604.13018v1.md
```

Source notes may link to normalized records in body text, but `source_ids` is the canonical machine-readable citation bridge.

## Validation Expectations

`normalize_verify.py` checks, against every selected record:

- required frontmatter fields exist and carry the documented types;
- `type` is `normalized_source`;
- `normalized_format` is a version this package accepts, or is absent on a record from
  this package's own normalizer;
- `source_id` matches a manifest record unless it starts with `manual:`, and the record
  lives at the path that source id resolves to;
- the record's `raw_paths` account for every raw path the manifest records, and a
  declared `raw_fingerprint` matches the manifest's;
- required sections are present in order;
- `parse_warnings` frontmatter and the `Parse Warnings` section are consistent.

Outside the per-record contract, lint checks that a manifest source has a normalized
record at all and that wiki source notes cite normalized records through `source_ids`.

Lint applies the contract itself to records that name a producing tool other than this
package's: such a record is accepted exactly as a native record when it conforms, and
emits MEDIUM `normalized_record_contract_violation` naming the first breach when it does
not. The finding is MEDIUM rather than HIGH so that one malformed record cannot freeze
orchestration across the workspace — the gates that decide whether a record can support
an answer, quote verification and the reopen check, fail closed on their own.

A record that names no producing tool at all is left alone by lint: it predates the
contract rather than claiming it, and re-normalization repairs it. `normalize_verify.py`
holds every record to the contract regardless of what it claims, so the stricter reading
is always available on demand.
